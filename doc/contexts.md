# Context knowledge

LilyPond scores are interpreted inside *contexts* — `Staff`, `Voice`, `Lyrics`, `ChordNames` and the rest — the objects that turn music into notation. A score names them twice over: a **context type** is the kind of thing (`Staff` engraves noteheads and clefs; `Lyrics` sets words under a melody), declared once, usually by LilyPond itself, occasionally by a user's own `\layout` block. A **context instance** is a particular one of them in a particular score — the `"vocals"` of `\new Voice = "vocals"` — created where a `\new` or `\context` is written and referred back to by name from `\change` and `\lyricsto` elsewhere in the same piece.

This document covers how ly-lsp reads both, keeps them in the [`Scope`](../src/vocabulary.rs) alongside commands, and uses them for completion, go-to-definition, semantic tokens and non-note detection. It is a companion to [`command-parsing.md`](command-parsing.md), whose "The table" section this one assumes.

## Reading them out of source

[`src/context.rs`](../src/context.rs) owns both readers, kept apart from `command::scheme` and `document`'s assignment-based one because a `\context { … }` block's directives (`\name`, `\alias`, `\accepts`, `\consists`, `\description`, …) mean nothing outside that block, and a `\new`/`\context` invocation is a distinct grammar shape from either.

**Context types** come from `\layout { \context { \name Staff … } }` and its kin. `context::read` matches an `escaped_word` immediately followed by an `expression_block`, wherever in the tree that occurs — a `\context` block is always nested inside `\layout`, `\midi` or a `\with`, never at the top level the way `SYMBOL_QUERY` wants for commands, so the query is deliberately unanchored. Not every match is a declaration: `\context { \Staff \override NoteHead.color = #red }` *modifies* an existing type and carries no `\name`, so `read_block` returns `None` for it — only a block that ends up with a name becomes a [`ContextType`](../src/context.rs). The directives themselves sit as a flat run of sibling nodes with nothing grouping a directive and its value, so `read_block` pairs them up by hand: a directive claims the following node only if that node isn't itself an `escaped_word`, which is what lets `\context { \Staff \name MyStaff }` — inheriting a whole type before renaming it — still read correctly even though `\Staff` takes no value of its own.

**Context instances** come from `\new Voice = "vocals" { … }` and `\context Voice = "vocals" { … }`. The grammar folds the keyword and the context type into one `named_context` node, so `read_instances` matches that node kind directly and reads its children positionally: type, then — only where a name was written — a `=` and a `symbol` or `string`. `\new Voice { c }` with no `= "name"` creates a context nobody can refer back to, so `read_named_context` returns `None` for it, the same reasoning `read_block` applies to an unnamed `\context { … }` block.

`\change Staff = "lower"` deliberately isn't read by either function. See "`\change` declares nothing" below.

## Three namespaces, one `Layer`

A [`Layer`](../src/vocabulary.rs) now holds three name-keyed tables — commands, context types, context instances — rather than one. They're kept apart rather than folded into a single map because the same bare word can mean different things in each: `Staff` could in principle be typed as a command, a context type, or (if some contrarian scoreographer named their voice that) an instance name, and a lookup that conflated the three couldn't tell `\new Staff` from a hover on the word `Staff` in running prose. `Scope::get`, `Scope::get_context_type` and `Scope::get_context_instance` each walk the same layer stack independently, with the same nearest-wins shadowing `command-parsing.md` describes for commands, through the shared `Scope::resolve`/`Scope::visible_via` machinery so a third namespace didn't need a third copy of "walk the layers, stop at the first hit".

`Layer::is_empty` and `Layer::len` had to grow to match: a layer that declares only a context type, no commands at all, must still count as non-empty, or `Scope::for_document`'s skip-empty-layers optimisation would make the declaration invisible to every scope and never re-analysed on edit. `Layer::len()` sums all three tables, so a figure like "607 entries" (see `command-parsing.md`'s "When it happens") is not 607 commands.

## Where the builtins come from

The install layer ([`src/install.rs`](../src/install.rs)) reads context types the same way it reads commands: parse a `.ly` file, keep what the readers find. But context types live in different files from commands, so [`CONTEXT_FILES`](../src/install.rs) — `engraver-init.ly` and `performer-init.ly` — is a second, separate list from the commands' `FILES`, read by a second loop in `install::load`.

LilyPond declares every context type **twice over**: `engraver-init.ly` declares it as an engraver context, `\description` and all, and `performer-init.ly` declares the same name again as a performer context, with everything but the description repeated. Letting the second occurrence replace the first outright would discard every description, since no performer copy carries one, so `install::load` merges the two field by field (`merge_context_type`): whichever side actually has a description wins, aliases are the union of both, and the name and spans come from whichever was read first (`engraver-init.ly`, since it's read first in `CONTEXT_FILES`'s order).

A context type's own name is bound as a command too — `\Staff` substitutes the `Staff` context definition, exactly as `\context { \Staff … }`'s inheriting shape relies on, so the install layer inserts a zero-argument `Variable` under each context type's name into the *commands* table, wherever a file-read command hasn't already claimed it.

The workspace layer works the same way for a user's own files: `Document::from_parts` calls `context::read` and `context::read_instances` on the document's own tree alongside the existing symbol/binding extraction, and stacks the results into the same `Layer` its commands live in — a file's `\layout { \context { \name MyStaff } }` is visible to every document that includes it, exactly as a `myFunc = …` definition would be.

## A file-scoped approximation

A context instance name is really scoped to the music expression that creates it. `\new Voice = "vocals" { … }` in one movement and an unrelated `\new Voice = "vocals" { … }` in another, never nested one inside the other, name two different contexts that merely happen to share a spelling — LilyPond itself tracks this by where the `\new` sits in the tree, not by the string alone. `ContextInstance` doesn't model that: `read_instances` and the `Layer` it feeds track one instance per *name*, file-wide, the same simplification `ContextType` and every command definition already make for the vocabulary they live in.

This is what makes completion and go-to-definition useful without a model of score structure — building the real one would mean tracking which music expression the cursor's `\change` or `\lyricsto` is nested in, and matching that against the expression tree each `\new` sits in. The price is that a `\change` or `\lyricsto` naming a duplicated instance name resolves to whichever occurrence was seen last (a `HashMap`'s insertion order, in effect), which need not be the one actually in scope at that point in the music. Worth revisiting only once a real score is observed to collide this way — no score has yet.

## What the features do with them

**Completion.** `\new`/`\context`'s first parameter offers every visible context type (`context_type_candidates`, in `command/mod.rs`), each labelled with its `\description` where it has one; their `= "name"` position, and `\change`'s and `\lyricsto`'s instance-name parameters, offer every visible context instance (`context_instance_candidates`). Both go through the ordinary `Command::completions` path when the parser can build a `CommandCall` at all, but a bare `\new ` with nothing typed after it parses too poorly for that — tree-sitter's error recovery leaves it wrapped in an `ERROR` node the note analyser never descends into, so no `CommandCall` exists to ask. `command_assist::context_argument_completions` covers that hole by reading the keyword straight out of the source text instead, then asking the same command for the same parameter-0 candidates, so the two paths never disagree about what's on offer.

Internal-only context types — `InternalGregorianStaff`, `InternalMensuralStaff` — exist only as intermediate bases the real Gregorian/Mensural types inherit from, and no real score ever names one directly, so `is_internal_context_type` filters them out of what completion *offers* while leaving them fully resolvable by `Scope::get_context_type` and `Scope::is_known` — a user's own type that inherits from one, as `VaticanaStaff` does, is never flagged as referencing something undefined.

**Go-to-definition.** `Document::context_type_at`/`context_name_at` recognise the cursor sitting on an `Arg::ContextType` or `Arg::ContextName` — neither is a `reference` symbol the ordinary `symbol_at` lookup would find, since both parse as a bare `symbol`/`string` meaningful only through the argument position a command's signature gives it. `DocumentGraph::goto_definition` tries these before falling back to the ordinary symbol path: an include path first, then a context type, then a context instance, then everything else — none can overlap with another, since each looks at a different node shape. `context_type_definitions`/`context_instance_definitions` then search the include closure for a file whose own layer declares the name, exactly as `definitions_in_effect` does for commands, except that neither `ContextType` nor `ContextInstance` carries a `redefines` chain to resolve a cursor position against, so a file that writes the same name twice yields whichever occurrence the layer kept (its last).

Go-to-definition on a *builtin* context type — `Staff`, unmodified by anything in the workspace — finds nothing. This is the same gap `command-parsing.md` records under "Later" for commands, now applying to context types too: an install-layer `ContextType` carries a `name_span` but no file, so a `Location` has nowhere honest to point. See that document's "Go-to-definition into the install" for the fix this is waiting on.

**Find-references and highlighting.** `DocumentGraph::references` and `document_highlights` try the same three namespaces in the same order go-to-definition does, so `\new MyStaff` and a `MyStaff = { … }` variable never report each other's occurrences. What counts as a reference comes from the parsed commands rather than from the `reference` symbols, for the reason go-to-definition already needs `context_type_at`: `Document::context_type_reference_ranges` and `context_instance_reference_ranges` walk each `CommandCall`'s arguments (through `command::flat_args`, shared with `semantic_tokens`, since the `= "name"` clause is one nested `Arg::Group`) and collect the spans of every `Arg::ContextType`/`Arg::ContextName` matching the name. `DocumentGraph::gather_references` then states the anchoring rule — only open documents whose include closure reaches a file that defines the name — once for all three namespaces rather than once per namespace.

Definitions and references have to be told apart by range, and a context instance is written the same way wherever it appears: the `"vocals"` a `\new Voice = "vocals"` creates is itself an `Arg::ContextName`, so `context_instance_reference_ranges` filters out whichever range `context_instance_creation` reports. That comparison only works because the two agree on their extent, and by default they don't — an `Arg::ContextName` spans the whole `string` node, quotes included, where `ContextInstance::span` spans only the contents — so `Document::unquoted` trims the argument's span to match. Context *types* need none of this: a `\context { \name Foo }` declaration is a different grammar shape altogether and never parses as an `Arg::ContextType` in the first place.

**Hover.** `command_assist::context_hover` runs before the command hover and claims the cursor only when it really is on a context argument, since the "only the command word" rule the rest of a call follows would otherwise describe `\new` while the cursor sits on `Staff`. A context type shows its `\description` — already read off the `\context { … }` block, and for a builtin already loaded from `engraver-init.ly` — under the aliases it also answers to, laid out the same way `describe` lays a command's synopsis out above its documentation, and led by the same italic attribution saying which file the type came from. A type with neither a description nor an alias gets no popup at all, on the same reasoning as an undocumented command: "`MyStaff` context" over the `MyStaff` you are already looking at is worse than nothing. An *instance* shows the type it was created as, which is the one thing about it a `\change` or `\lyricsto` site doesn't say for itself.

**Semantic tokens.** `Arg::ContextType` and `Arg::ContextName` are emitted as `SemanticTokenType::TYPE` and `VARIABLE` respectively, alongside the `KEYWORD` tokens `command-parsing.md` already describes — the same "the grammar can't tell this bare symbol apart from any other without command context" gap, just for these two namespaces. `Staff` in `\new Staff` is, to the grammar, an ordinary `symbol` node; `"vocals"` in `\lyricsto "vocals"` an ordinary `string`. See [`semantic_tokens.rs`](../src/semantic_tokens.rs)'s module doc for why the other argument kinds don't get their own type.

**Non-note detection.** `\new`/`\context`'s body isn't always read as ordinary note music — `\new Lyrics { la la la }` and `\new ChordNames { c2:m }` hold words and chord symbols respectively, not pitches. `NewContextCommand::music_context` decides this per call by asking `is_non_note(type_name, scope)`, in [`src/command/new_context.rs`](../src/command/new_context.rs).

## The hand-maintained non-note list

`is_non_note` checks `type_name` — or, where the scope has a `ContextType` on record for it, that type's declared aliases too — against `NON_NOTE_CONTEXT_ROOTS`: `Lyrics`, `NullVoice`, `ChordNames`, `FretBoards`, `FiguredBass`, `Dynamics`, `DrumStaff`, `DrumVoice`. This has to be hand-maintained because LilyPond's own initialisation files don't mark a context type as "reads its body as music" or not anywhere this reader can find — unlike a context type's name, aliases and description, which come straight off the `\name`/`\alias`/`\description` directives, "does this hold notes" is a semantic fact about the *engraver*, not a declared property of the context block.

The list names *roots* rather than every non-note type, because aliases are followed: a user's own `\context { \name MyLyrics \alias Lyrics }` is non-note by inheriting from `Lyrics`, without needing its own entry. The list is checked before falling back to a plain name match when the scope has no declaration for the type at all — a looser fallback than `Scope::is_known`'s CamelCase rule, since it fires per name (an ordinary typo included) rather than only when the whole install failed to load, but the module doc on `is_non_note` argues this costs nothing observable: every name in the list is a builtin any successfully loaded install already declares, so with a real install behind the scope this branch is only ever reached by a name that isn't a root either way.

## `\change` declares nothing

`\change Staff = "lower"` moves the music that follows into an *already-existing* context, rather than bringing one into being — LilyPond's own manual says as much by omission: `\new`'s documentation says it "creates a fresh context", `\context`'s says it "finds the existing context… creating one only if none is found", and `\change`'s says neither, describing only that it changes which context an interpretation is pointed at. So `\change` is a *reference* to a context-instance name this reader must already know, not a second source of definitions for the namespace `context::read_instances` builds — matching how a command *call* isn't read as a fresh command definition either.

Grammatically this falls out for free: `\change` never parses as a `named_context` node the way `\new`/`\context` do, so `read_instances`' node-kind query simply never matches it, confirmed by a test (`change_refers_to_an_instance_rather_than_creating_one`). Its target reaches the namespace the ordinary way any reference does, through `ArgKind::ContextName`'s parsed span and `Scope::get_context_instance`. `\lyricsto`'s voice name works identically, for the same reason.

## Limitations

- **Instance names are file-scoped, not expression-scoped** — see above. The cost is a possible wrong resolution where two unrelated instances share a name in one file; not observed in practice yet.
- **Go-to-definition on a builtin context type finds nothing** — the install-layer `ContextType` carries no file. Cross-referenced above; tracked as a "Later" item in `command-parsing.md`, shared with the equivalent gap for commands.
- **`NON_NOTE_CONTEXT_ROOTS` is a hand-maintained list**, not derived from anything the install ships, and could miss a context type a future LilyPond release adds. Its aliases-followed design limits the maintenance surface to roots, not every possible non-note type, but a genuinely new root (not an alias of an existing one) would still need adding by hand.
- **A `ContextType` carries no `redefines` chain.** Unlike a command binding, a file that writes `\name Foo` twice inside two different `\context { … }` blocks has no notion of "which one is in effect at this position" — the layer just keeps the last, and go-to-definition lands there regardless of where the reference sits. The same is true of `ContextInstance`. Neither has been observed to matter in a real score; `command-parsing.md`'s "A redefinition replaces from the point it appears" logic exists for commands because real files do redefine variables mid-file, and no comparable pattern has shown up for contexts.
